This is the standalone quarrel.io repository: `diamster/falls-hacks-2026-quarrel`. All future quarrel.io changes and pushes belong here. The Next.js app lives at the repository root. Do not use `falls-hacks-2026-ideas` or the SFU campus checkout for this app.

## Stage 5 (current) — Lawyer Sidekick Debate

Stage 5 is authorized on `quarrel-stage-5`. The full specification is `docs/stage-5-handoff.md`; read it first. It is the explicit user instruction that the Stage 4 rules below require, and where it conflicts with them, the handoff wins:

- Replace the opening/rebuttal/question phases with planner-generated subtopics, per-subtopic chess clocks, AI lawyer rewrites, judge summaries per subtopic and a final jury verdict.
- Remove Ask Judge chat, clarification questions, the concealed opening reveal and the placeholder verdict from the playable flow. Keep their existing tables and Cloud data; never drop, reset or replay.
- Only the jury job may name an outcome (side A, side B or split). Lawyer, judge and planner jobs still must not.
- Objections are out of scope; do not implement the earlier "Stage 5 — Interactive Objection System" brief.
- The provisional defaults in section 3 of the handoff are unconfirmed; ask the user before deviating from them.

All other rules below (server-authoritative state, `auth.uid()` identity, RLS, no service role, server-only Gemini key and judge capability, Cloud migration review, testing and documentation) still apply. Record Stage 5 results in `docs/stage-5-testing.md`.

## Stage 4 rules (still apply unless superseded above)

Stage 4 is authorized on `quarrel-stage-4`: preserve the Stage 1–3 application, all four original themes (Jungle, Superhero, Detective and Courtroom), centralized theme/asset configuration and multiplayer lobby. Add the server-side Gemini judge, shared direct judge chat, contextual clarification questions, theme personalities and judge reactions. Preserve agreed topics/opposing positions, host start, sequential opening/rebuttal/question turns, server deadlines, concealed simultaneous opening reveal, and a placeholder verdict without a winner. Keep room creation/joining, verified anonymous sessions, readiness, connection status, refresh recovery and the two-seat limit working. Preserve the original Jungle SVG artwork and the Stage 1 local-only preview at `/preview`.

The user explicitly selected Gemini for Stage 4; do not introduce another provider or put API calls in browser code. No AI-generated topics, real objections/verdicts, account registration, voice/video or Stage 5 without a new explicit user instruction. Every theme must reuse the shared engine and neutrality policy; personality affects wording and reactions only, never standards or outcomes. Objection/verdict animation styles remain unimplemented configuration.

Ask Judge and Submit Argument are separate actions. Only the active authenticated participant may ask, within the stored per-turn quota and server rate limit. Asking never submits an official argument, advances a phase or extends a deadline. All judge conversations are shared with both room members and restored after refresh. Reserve requests with idempotency before generation, claim a model job at most once, and save validated replies before display. Generate both clarification questions together once after the rebuttals; persist them before starting the full 30-second answer clock. Never disclose hidden official openings to the shared judge context before reveal, including the requesting player's own opening.

Keep `GEMINI_API_KEY` and `JUDGE_SERVER_SECRET` server-only in ignored environment configuration; never commit, print or expose either. `judge:setup` preserves existing environment settings and emits only hash registration SQL. The private capability hash protects model-job authority in addition to verified player membership; it is not a service-role bypass. All instances for one project must use its registered capability. Bound context, output, request duration and message size. Use structured responses, validate on the server and in PostgreSQL, and preserve no-key demo and recoverable fallback behavior. Treat participant text as untrusted data separate from governing instructions. Never let model output mutate official state, invent evidence or choose a winner. Threats, abuse or coercion require safer redirection. Prompt/output tests are defense in depth, not proof that all possible model responses are safe.

Use stable theme/character IDs and the central resolvers; do not scatter theme-specific multiplayer branches through the app. Invalid rendered IDs fall back safely; invalid theme writes are rejected by the server and database. Only verified Player A may change a room theme. The host start RPC must lock the theme and topic atomically after checking both topic approvals, opposing positions, readiness and current connections. Readiness alone must never start a debate. Proposal edits/requested changes invalidate readiness and approvals; stale proposal revisions must not authorize actions.

Stage 8/9 preparation is types/configuration only: keep player identity, optional character choice/team membership and round-specific representative assignment separate. No character-selection UI or writes, extra selectable characters, teams, team chat, representative selection/rotation or team rules. Solo is the only playable mode, with capacity two; future mode metadata cannot expand the current database constraint or bypass authorization.

All room mutations derive identity from the verified session and PostgreSQL `auth.uid()`. Never accept a player ID/slot as mutation authority. No browser or server Supabase service-role bypass. Keep private room data behind RLS and state-changing RPCs; preserve the race-safe two-slot constraint. The user has authorized Supabase Cloud project `exjdvtqsalnkghyohyuh` for this app and its integration checks. Use its publishable key with verified anonymous sessions; the separate Gemini key and server capability are never client-accessible. Never commit runtime credentials. The current user explicitly requires Supabase Cloud for this stage; do not switch their app to local Docker. Optional isolated local CI configuration may remain, but test the current connected Cloud project and report what actually ran. Preserve keyboard accessibility, reduced-motion support and responsive layout.

Before hosted database changes, inspect the existing schema and migration history. Earlier migrations, including Stage 4, may already be applied under management-tool timestamps different from repository filenames; reconcile verified history before a CLI database push. Do not replay the initial schema or reset Cloud. Preserve the insert/update-only Realtime publication privacy guard and check its project-wide impact before applying to another project. Read `docs/stage-2-5-cloud.md`, `docs/stage-3-testing.md` and `docs/stage-4-testing.md` for the current target and verification records. Review new migrations before applying them; preserve all existing tables and data. The legacy Stage 3 authenticated start RPC remains compatible; application starts must use the judged-start RPC.

Before handing off, run `npm run check` (automated component tests with coverage, then the production build) and inspect the desktop/mobile UI and local preview interactions in a browser. Keep Stage 1–3 behavior tests passing; fix causes instead of lowering coverage thresholds or weakening assertions. Use the authorized Cloud integration suites for this stage; do not silently substitute Docker checks. Run `npm run test:debate` with the remote opt-in against the configured Cloud project, including genuine deadline expiry. Exercise the Cloud development backend with `QUARREL_ALLOW_REMOTE_TESTS=true` for `test:supabase`, `test:api` and `test:judge` against the running app. The judge suite covers shared messages, active-player authorization, duplicate prevention, quotas, opening privacy, saved questions, full answer timers and refresh. The database is the authority for all debate transitions. Do not accept browser player IDs, phase changes, deadlines or winner fields. Opening text belongs in private storage and must never leak through public room rows, direct reads or Realtime payloads before both opening turns finish. Explicit leave is now authorized: retain historical player slots/names and debate records while detaching only the verified caller's membership. Never let a new person inherit a departed seat. Preserve the caller's Auth identity/cookies for subsequent rooms. Expected room IDs are stale-page guards, not identity; check them under the same database lock as room mutations. A delayed action from another tab must not mutate the caller's newer room. Require explicit product confirmation before leaving; cancellation or failure preserves the saved seat. Test same-browser leave/create/join, closed invitations, peer record preservation and stale-tab rejection with `test:leave`.
